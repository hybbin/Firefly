## 🛠️ 第三幕：深入 QNAP 底层——破解 Qnet 与旁路由的“暗度陈仓”

小芝麻通过 SSH 顺利握手登入 NAS 新主 IP **`192.168.86.67`**，把威联通 Container Station 的网络拓扑、网桥结构与路由表底牌彻彻底底翻了一遍。

真相很快水落石出——这是一场威联通底层特有的 **“Qnet 驱动执念”** 与 **“旁路由网关校验”** 双重夹击引发的事故！

### 1. 病灶一：僵尸网络与物理网卡死绑
威联通 Container Station 默认推荐使用的网络模式是 `qnet`（Macvlan 的一种增强实现），它允许每个容器拥有家庭局域网内的独立真实物理 IP。  
但 Qnet 有一个致命特性：**它在创建时必须严格绑定到某一块特定的物理网卡设备（`iface`）**！  
在拔线前，系统内运行着 4 个自动生成的 Qnet 网络：
- `qnet-dhcp-eth0-*`
- `qnet-static-eth0-*`

它们全部铁打不动地咬死在物理网卡 **`eth0`** 上。随着网线一拔，`eth0` 的链路状态瞬间沦为 `NO-CARRIER`。即使宿主机的 `eth1`（`192.168.86.67`）活蹦乱跳，只要挂在 `eth0` 上的容器，发出的数据包就会全部投向虚无的断线黑洞！

```bash
# eth0 物理链路已断，但旧 Qnet 网络仍然僵死在 eth0 上
92: eth0: <NO-CARRIER,BROADCAST,MULTICAST,UP> mtu 1500 ...
```

### 2. 病灶二：为什么哥哥手动重建容器会被断然拒绝？
这正是整起事件中最隐蔽、最坑人的核心玄机！  
哥哥在尝试重新创建容器时，通常会按照家庭网络的通用直觉，将网关顺理成章地填为主路由器 IP（`192.168.86.1`）。  
然而，小芝麻查验宿主机的网络拓扑后发现：
- 剩余的 `eth1` 物理网卡，在威联通内部被绑定到了虚拟交换机网桥 **`br1`**；
- 重点来了！`br1` 网桥在宿主机路由表中的默认网关，配置的并不是主路由 `.1`，而是承担全家透明分流与出海大任的**旁路由——`192.168.86.86`**！

威联通的 `qnet` 驱动在底层内核模块中编写了近乎苛刻的参数校验：**创建 Qnet 网络或挂载容器时，指定的网关必须与宿主机该网卡当前路由表里的 Gateway 完全保持一致**！一旦哥哥填了 `.1`，内核校验即刻报错拦截，导致创建流程直接崩盘，连原容器都被误操作带走了。

破译了这个“密码”，接下来的解法便如顺水推舟般豁然开朗！( •̀ ω •́ )✧

## 🚢 第四幕：赛博方舟的“诺亚大迁徙”——十数容器无损大回魂

既然摸清了威联通脾气，小芝麻果断操刀，为整座 NAS 开启了一套教科书级别的网络重构与全量迁移方案。

### 1. 铸造新锚点：创建 `qnet-static-br1`
首先，小芝麻在宿主机内基于活动的 `br1` 虚拟交换机，精准构建起全新的专属静态网络：
```bash
docker network create -d qnet \
  --opt iface=br1 \
  --subnet=192.168.86.0/24 \
  --gateway=192.168.86.86 \
  qnet-static-br1
```
网卡对准 `br1`，网关严格对齐旁路由 `192.168.86.86`，地基稳稳筑牢！

### 2. 重建浏览器容器：Stealth 隐形战机满血复活
接着，小芝麻着手修复哥哥心心念念的浏览器基础设施——**Browserless Chrome**：
- **镜像版本**：调用本地现成的 `browserless/chrome:latest` 生产镜像；
- **网络注入**：直接接入 `qnet-static-br1`，锁定固定 IP **`192.168.86.117`**；
- **高阶参数还原**：
  - 注入 `DEFAULT_STEALTH=true`，重新激活强大的反爬虫风控绕过能力；
  - 预设公共双 DNS 解析器（`8.8.8.8` 与 `223.5.5.5`）；
  - 挂载 `/tmp` 内存临时目录与最大并发连接优化参数。
- **端到端活体验证**：容器拉起后，不仅 HTTP `/json/version` 瞬间响应 200，小芝麻还亲自调用 Hermes 底层的 `browser_cdp` 驱动工具，直连 `192.168.86.117:3000` 执行了一段真实的 Headless 交互探针，确认连通无误！
