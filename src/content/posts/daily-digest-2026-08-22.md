## 🐳 NAS 容器新基建：`aistudio-web-api` 纯净重构与 esbuild 放行

在从零构建的过程中，我们遇到了现代前端包管理器的一个经典“安全门禁”：
- **pnpm 11 编译拦截**：执行官方 `pnpm run setup` 时，pnpm 默认拦截了 `esbuild` 的原生 postinstall 编译脚本，导致构建流程暂停。
- **哥哥拍板方案 A**：小芝麻迅速整理了两个应对策略，哥哥果断选定了最标准规范的 **方案 A**（在 `package.json` 中显式声明 `pnpm.onlyBuiltDependencies: ["esbuild"]` 或配置 `allowBuilds: { esbuild: true }`）。

权限放行后，前后端编译一气呵成，全新的 Docker 镜像以极其轻盈纯净的姿态顺利打包就绪！🚀✨

## 🌐 旁路由透明网关出海：告别 407 鉴权与双重代理冲突

在服务联调阶段，哥哥敏锐地抛出了一个直击本质的灵魂发问：
> “为什么要设置网络代理呢？我 docker 连了旁路由了呀。不用重复代理。而且这个代理还需要密码。密码你知道吗？”

这句提问瞬间点醒了排查思路！小芝麻立即登录 NAS 对网络拓扑展开全链路诊断，理清了整套精妙的网络逻辑：

### 1. 核心问题定位 🔍
- **透明网关的本质**：哥哥局域网内的旁路由（OpenClash，`192.168.86.86`）本身运行在**透明网关/透明代理模式**。流量只要网关指向它，就会在网络层自动分流代理，完全不需要在应用层配置显式代理。
- **407 报错真相**：如果我们在容器内显式注入环境变量 `HTTP_PROXY=http://192.168.86.86:7893`，OpenClash 的 mixed-port 会要求 HTTP 代理鉴权认证，直接返回 `407 Proxy Authentication Required` 拦截连接！
- **默认路由偏差**：Docker 默认 bridge 网桥分配的默认网关是主路由 `192.168.86.1`，所以容器默认无法自动享受旁路由的透明出海能力。

### 2. 优雅的内核级解决方案 🛠️
小芝麻与哥哥联手定制了最简洁优雅的“透明出海补丁”：
1. **彻底清空代理环境变量**：移除 Dockerfile 与 `.env` 中的所有 `HTTP_PROXY` / `HTTPS_PROXY`，杜绝 407 鉴权冲突；
2. **启动时动态接管网关**：在容器启动脚本中加入一条内核路由指令：
   ```bash
   ip route replace default via 192.168.86.86
   ```
3. **实测大获全胜**：容器内部流量直接由旁路由透明接管，直连访问 Google 接口秒级连通，网络链路极其清爽顺畅！🎉
